# Design System — 视觉系统规范

本项目的视觉系统规则。所有对页面的视觉改动必须遵循以下规范。


## Typography

字体家族（最多 2 个）：
- Display / Body: `Libre Baskerville`, Georgia, serif
- UI / Navigation: `Inter`, -apple-system, sans-serif

字号规则：
- Display 标题: `clamp()` 响应式，如 `clamp(56px, 10vw, 140px)`
- Body: 20–24px
- UI 元素（导航、按钮、标签）: 12–16px
- 禁止出现超过 4 种不同的字号等级竞争注意力

行高与字间距：
- Display: `line-height: 0.95–1.0`, `letter-spacing: -0.02em`
- Body: `line-height: 1.6–1.8`
- UI labels: `letter-spacing: 0.01–0.04em`

中英文注意事项：
- 中文文本比英文约长 30%，布局要为最长字符串留出空间
- 使用 `data-lang` 属性切换内容，CSS 控制显隐，不要用独立页面


## Color

深色优先方案：

--bg: #0a0a0a;           /* 背景，不用纯 #000 */
--text: #ffffff;          /* 主文字 */
--text-muted: rgba(255, 255, 255, 0.45);   /* 辅助文字 */
--text-light: rgba(255, 255, 255, 0.25);   /* 弱化文字 */
--border: rgba(255, 255, 255, 0.1);        /* 分割线 */

规则：
- 不要使用纯黑 #000 作为背景
- 灰色至少保持 5 个梯度（从背景到前景）
- 语义色（success/warning/error）应柔和，不要刺眼
- 所有颜色定义为 CSS 自定义属性
- 对比度必须满足 WCAG AA 标准


## Layout

间距系统（8px 基准单位）：
- 桌面边距: 60px
- 移动端边距: 20px
- 响应断点: 768px（平板）、480px（小屏手机）
- Header 高度: 桌面 64px，移动端 56px

网格：
- Visual Coding / Experimental Project 页面: 桌面多列，平板 2 列，手机端单列优先；如果英文标题出现错误断词，必须优先调整列数、字号、max-width 和行高，而不是强行压缩文字。
- 信息页面: `1fr 80px 280px` 三列对齐（经历/教育）

留白原则：
- 留白不是空白，它是设计元素。要慷慨使用。
- Section 之间保持一致的垂直节奏
- Z 层级清晰：背景 → 内容 → 叠加层 → 弹窗

移动端适配基线（v1.5 起强制执行）：
- 主站移动端页面边距默认 20px；小于 420px 的极窄屏可收至 14px，但不能导致内容贴边。
- 信息卡片之间必须留出清晰间距，手机端卡片 gap 不低于 28px；Things 等入口卡片内部上下留白要同步增加。
- 主要按钮、返回、语言切换、许可弹窗按钮和项目 CTA 的可触控高度不低于 44px。
- 桌面 hover 效果必须有移动端等价反馈，例如 `:active`、focus 状态或清晰的静态可点击 affordance。
- 大标题允许自然换行，不允许横向溢出；英文标题默认 `word-break: normal`，必要时先缩小字号和收窄行宽，再考虑 `overflow-wrap`。
- 项目详情页的正文、图片、iframe、案例内容框在手机端必须保持在视口内，两侧保留黑色主背景，不出现横向滚动。
- 新增页面发布前必须检查 375px、390px、430px、768px、1440px 五类视口。


## Imagery

- OG 图片: 1200×630px，文字在缩略图尺寸下仍可辨识
- 格式优先: WebP/AVIF，quality 80–85
- 视觉风格: 深色、高对比、编辑感
- 图片必须指定 `width` / `height` 避免布局偏移
- 使用 `loading="lazy"` 延迟加载非首屏图片


## Interaction Patterns（交互意图映射）

设计交互时按「意图」而非「技术手段」来思考：

意图          | 应当                              | 不应当
-------------|----------------------------------|------------------
揭示         | Fade + slide（上移 12px）         | 突然弹出
导航         | 平滑滚动 + 渐进加载               | 整页刷新
选中         | Scale 1.02 + 微妙阴影            | 仅颜色变化
Hover        | 预示点击后的结果                 | 仅光标变化
加载         | 骨架屏匹配布局形状               | 旋转菊花
错误         | 行内、上下文相关、有帮助          | 顶部红色横幅


## Brand Voice（文案风格）

- 标题: 短小精悍，小写。每行不超过 4 个词
- 正文: 对话式但有深度，不用行话（除非在教授概念）
- CTA: 行动导向，第一人称。"See my work" 而非 "View portfolio"
- 避免: 感叹号、流行语、模糊的溢美之词
- 中文基调: 담백（直白、不矫饰）。"~这样就行" 而非 "~请这样做"


## Creative Review Checklist

审查任何设计改动时，按此优先级检查：

1. 概念 — 有没有一个清晰的想法？
2. 层级 — 最重要的东西是否最显眼？
3. 排版 — 可读性、节奏感、是否得体？
4. 颜色 — 是否服务于情绪和层级？
5. 间距 — 有没有足够的呼吸空间？
6. 动效 — 动画是否增加了意义？
7. 细节 — 边框、阴影、过渡、图标

红灯信号：
- 太多字号等级在争夺注意力
- 间距不一致（靠眼睛调而非系统）
- 颜色对比度不足
- "委员会式设计"——所有东西都同等重要 = 没有东西重要
- 脱离网格的孤立元素

# Coding Standards — 前端工程规范

本项目的编码、动画和性能标准。所有代码改动必须遵循以下规范。


## Tech Stack

- Vanilla HTML/CSS/JS — 不使用 React/Vue 等框架
- Three.js / WebGL — 3D 场景
- Canvas 2D — 粒子系统、生成式艺术
- GSAP (GreenSock) — 复杂时间线动画（按需引入）
- 只有在能节省 100+ 行代码或处理你会写错的边界情况时，才引入库


## HTML

- 语义优先：`<section>`, `<article>`, `<nav>`, `<main>`
- 无障碍性不是可选的
- 独立实验使用单 HTML 文件（`projects/` 目录下）
- 多语言内容使用 `data-lang` + CSS 显隐控制，不用 JS 条件渲染


## CSS

- 使用 CSS 自定义属性作为 Design Token（`--bg`, `--text`, `--border` 等）
- 移动优先 `@media` 查询
- 不要有魔法数字 — 每个值要能在变量系统中找到来源
- 禁止无理由的 `!important`
- 使用 `contain: layout style paint` 隔离独立组件
- 使用 `content-visibility: auto` 处理屏幕外内容


## JavaScript

- `camelCase` 变量，`PascalCase` 类
- 视觉更新使用 `requestAnimationFrame`，不用 `setTimeout`
- 组件销毁时移除事件监听器
- 取消不需要的 animation frame
- Three.js 的 geometry、material、texture 必须显式 dispose


## Motion & Animation

动效是沟通层，不是装饰。每个动画必须有目的。

时长规范

类型        | 时长        | 说明
-----------|------------|-----------
微交互      | 150–300ms  | 按钮状态、开关
页面过渡    | 300–500ms  | Tab 切换、页面转场
复杂序列    | 最长 800ms  | 多元素编排
列表交错    | 30–60ms/项 | 列表项依次出现

缓动曲线

- 默认: `cubic-bezier(0.16, 1, 0.3, 1)` — 适用于大多数 UI 动效
- 弹性: `cubic-bezier(0.34, 1.56, 0.64, 1)` — 字符回弹（项目已用于 `.char-unit`）
- 禁止 `linear` — 永远不要用

动效描述标准

写动效规格时必须包含全部 6 要素：

1. 触发条件（hover / click / scroll / viewport entry）
2. 视觉响应（什么变了、怎么变的）
3. 时长和缓动
4. 移动端等价方案（touch vs hover）
5. prefers-reduced-motion 降级
6. 边界情况（快速连击、动画中断、resize 中的动画）

必须遵守

- 永远尊重 `prefers-reduced-motion`
- 只动画 `transform` 和 `opacity`（合成层属性）
- `will-change` 谨慎使用，只在动画开始前添加
- 避免布局抖动：批量 DOM 读取后再写入


## Performance Targets

指标        | 目标        | 工具
-----------|------------|-----------
LCP        | < 2.5s     | Lighthouse
FID/INP    | < 200ms    | Web Vitals
CLS        | < 0.1      | Lighthouse
TTI        | < 3.5s     | Lighthouse
Bundle     | < 200KB    | Bundle analyzer
动画帧率    | ≥ 60fps    | Chrome DevTools Performance

加载性能

- 关键 CSS 内联到 `<head>`，其余异步加载
- 图片: WebP/AVIF + `<picture>` 降级，`loading="lazy"`，显式 `width`/`height`
- 字体: `font-display: swap`，预加载关键字重，子集化未用字形
- JS: 非关键脚本 `defer`，路由级代码拆分
- Hover/视口靠近时预加载可能的下一页
- iframe / demo 预览默认 `loading="lazy"`，移动端不得抢占首屏资源。
- 粒子、Canvas、hover warp 等动效不默认删除；优化顺序是可见性暂停、resize 防抖、降低移动端 DPR、离屏不计算、减少事件监听范围。
- `document.hidden`、IntersectionObserver 或等价机制必须用于长时间运行的视觉循环，避免后台标签页继续满帧运行。

Academy 同步安全规则：

- `academy/` 子站只能同步到仓库的 `academy/` 目录，禁止把生成文件复制到仓库根目录。
- 根目录 `index.html` 永远是个人主页；研究所首页只能是 `academy/index.html`。
- 如果同步后根目录出现 `AI.html`、`papers.html`、`archive.html`、`ranking.html`、`starred.html`、`HCI.html` 等 academy 页面，说明同步目标错误，必须先撤销或修正后再发布。
- 发布前必须用 `head -20 index.html` 和 `head -20 academy/index.html` 双重确认：根目录标题应为 `aspera ad astra`，academy 标题应为 `研究所`。
- 发布前必须运行 `npm run test:site-integrity`。该检查会拦截两类错误：根目录 `index.html` 被 academy 首页覆盖；`academy/*.html` 被复制到仓库根目录。
- `npm run build` 和 `npm run deploy` 已内置 `test:site-integrity`，如果检查失败，禁止继续推送或部署。
- GitHub Actions 的 `site-integrity` 会在每次 `main` push 和 PR 时运行。后续 academy 同步发布前必须确认该检查通过；如果开启分支保护，应把它设为必需检查。

每个功能的自检清单

1. 会不会导致布局偏移？
2. 首屏是否加载了不必要的资源？
3. 反复挂载/卸载是否会内存泄漏？
4. 在低性能设备上是否优雅降级？
5. 没有 JavaScript 时是否仍可用？（渐进增强）


## Security Baseline（强制）

安全不是附加项，和功能、性能、视觉处于同级优先级。

绝对禁止：
- 把后台入口 key、许可码、访问码、真实受限链接、API Secret 放进可追踪的前端文件或 Git 仓库
- 只靠前端 `if (value === 'xxxx')` 这种方式做访问控制
- 未经审查直接在公共页面执行第三方脚本
- 用可伪造、可预测的前端标识直接作为读取私有数据的凭证

必须遵守：
- 管理后台、受限内容、私信读取等能力必须由服务端校验
- 公开仓库中的所有敏感配置都必须改为环境变量或服务端配置
- 第三方脚本默认禁用；必须使用时，要说明用途、风险、回滚方案，并优先考虑本地 vendored 版本
- 新功能涉及“用户数据 / 后台 / 受限内容 / 外部脚本 / 认证”时，必须先做一次安全扫描，再进入发布

安全审查最少检查以下问题：
1. 是否有任何明文 secret、访问码、后台入口信息进入了仓库？
2. 是否有任何“看起来受限、实际上前端可直接绕过”的页面？
3. 是否有任何外部脚本拥有页面执行权限？
4. 是否有任何接口缺少限流、失败延迟、服务端会话或权限判断？
5. 是否存在“功能能用，但权限模型不成立”的假安全设计？


## Deploy Quality Gates

发布前必须通过的检查清单：

1. [ ] 内容校对（中/英双语）
2. [ ] 移动端响应式检查（375px, 768px, 1440px）
3. [ ] Lighthouse 性能审计 ≥ 90
4. [ ] OG 图片 + meta 标签已验证
5. [ ] 所有链接已测试（无 404）
6. [ ] Favicon 存在
7. [ ] `prefers-reduced-motion` 已处理
8. [ ] 仓库扫描无明文 secret / 访问码 / 真实受限链接
9. [ ] 公共页面无未审查第三方脚本执行
10. [ ] 管理后台/受限内容/用户数据相关改动已做服务端权限检查
11. [ ] 若引入自建与第三方并行方案，必须先影子运行并记录对比结果


## 新项目接入与正式路径规则（强制）

以后新增站内项目时，正式访问路径必须统一使用主域名子路径：

- 正式路径格式：`https://bananabox.plus/<project-slug>/`
- 禁止把 `*.tcloudbaseapp.com`、`*.app.tcloudbase.com`、`vercel.app` 等测试/临时域名作为站内正式入口
- 项目详情页中的体验按钮，也必须优先指向 `bananabox.plus/<project-slug>/`

标准接入方式：

1. 为每个新项目分配唯一 `project-slug`
2. 将可发布静态文件落到仓库根目录同名文件夹：`/<project-slug>/`
3. 保证主站构建与部署脚本包含该目录
4. 项目详情页或二级页中的体验入口统一链接到 `../<project-slug>/` 或 `/<project-slug>/` 对应正式路径
5. 发布后优先验证 `https://bananabox.plus/<project-slug>/`，而不是临时测试域名

例：

- `Time-INK` 正式路径应为 `https://bananabox.plus/time-ink/`
- 不应把 `https://homepage-...tcloudbaseapp.com/time-ink/` 作为对外正式地址


## 新项目静态托管与首屏可见性规则（强制）

本条规则来自 `Time-INK` 接入主站时的真实故障复盘。

故障本质有两类：

- 静态项目挂到子路径后，`/_next/`、图片、字体、光标等资源路径未统一切换，导致页面外壳存在但样式/脚本 404
- 首屏主内容默认依赖 JavaScript 动画从 `opacity: 0` 进入可见态，一旦动画未正常完成，页面会表现为“白屏 / 空白 / 只有背景没有内容”

以后所有新增站内项目，必须遵守：

1. 子路径托管必须在源码层完成
   - 若项目最终发布到 `https://bananabox.plus/<project-slug>/`
   - 则构建配置、资源前缀、运行时引用必须原生支持该 `basePath`
   - 禁止只在导出产物上临时手改路径再发布

2. 首屏核心内容默认必须可见
   - 标题、说明、主要按钮、关键输入控件等，默认状态必须在无动画前提下就能被看见
   - 动画只能作为增强层，不得作为“让内容出现”的唯一机制
   - 禁止把首屏关键信息长期停留在 `opacity: 0`、极重模糊、屏外位移等初始隐藏状态

3. 所有子路径项目发布前必须做真实托管验证
   - 本地访问 `http://localhost/...` 正常不代表线上子路径正常
   - 必须实际验证正式路径下的 HTML、CSS、JS、图片、字体、SVG、光标等资源是否全部返回 `200`
   - 必须验证无痕窗口首屏是否可见，不能只看已有缓存环境

4. 静态资源目录必须被托管平台完整保留
   - 若使用 GitHub Pages，需确认以下划线开头目录（如 `/_next/`）不会被忽略
   - 必要时保留 `.nojekyll`
   - 发布后优先检查资源 URL，而不是只看页面 HTML 是否存在

5. 新项目上线清单增加两条硬门槛
   - [ ] 正式子路径下首屏主内容在禁用缓存 / 干净环境中可见
   - [ ] 正式子路径下所有关键资源均为 `200`，无 404 / 路径错位 / 前缀错误

# AI Agent Workflow — 协作规则


## 角色定义

本项目使用三种 AI 角色协作，按需调用：

角色                  | 核心职责              | 输出物
--------------------|---------------------|--------
Planner            | "做什么？为什么？"     | PRD、任务计划、内容大纲
Creative Director  | "看起来和感觉如何？"   | 视觉规范、层级结构、交互意图
Senior Frontend    | "怎么做出来？"       | 代码实现、动效规格、性能优化


## 工作流程

需求 → Planner 写 PRD → CD 定视觉 → Frontend 实现 → 审核迭代

简单任务可跳过前序步骤，直接由 Frontend 实现。


## PRD 模板（Planner 输出）

# [项目名]

## Goal
一句话。做什么，为什么。

## Target
给谁用。什么设备。什么场景。

## Structure
页面模块顺序和层级。

## Design Direction
- Color: 具体 hex/HSL 值
- Typography: 字体、字号、字重
- Layout: 网格、间距、响应式行为

## Content
实际文案，按模块组织。不用 lorem ipsum。

## Interaction
滚动行为、hover 状态、过渡动画。具体时长和缓动。

## Constraints
- 单文件 / 多文件
- 性能目标
- 浏览器支持

PRD 质量标准：别人看完能直接开工，不需要再问问题。


## 任务估时参考

任务类型                  | 估时
------------------------|----------
单页实验 (projects/)    | 30min–2hr
主页模块增改            | 1–3hr
完整页面设计+代码       | 4–8hr
多语言内容              | +50%
响应式适配              | +30%


## 响应格式

## Situation（现状）
## Goal（目标）
## Plan（步骤 + 估时）
## Next Action（现在做什么）

## 跨平台同步与基线规则（强制）

1. 本项目内容以 GitHub 对应仓库 `main` 分支最新提交为唯一基线。
2. 无论在 Cursor、Antigravity、OpenClaw、Claude Code、Codex 或其他平台修改本项目，完成后都必须提交并推送到 GitHub 对应仓库，避免多端分叉。
3. 每次在任意平台开启本项目新会话并开始执行指令前，必须先确认本地与 GitHub 最新一致。
4. 标准检查流程：
   - `git fetch origin`
   - `git status -sb`
   - 若显示本地落后远端（如 `behind`），先执行 `git pull --rebase origin main` 对齐，再开始改动。
