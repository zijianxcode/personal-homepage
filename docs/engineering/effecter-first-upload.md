# Effecter 首次上传修复（2026-10-11）

用户反馈电脑、手机首次上传等待很久，或者第二次上传才正常。

直接原因是生产保护脚本给 HTML 中的 ESM 入口增加了 `?vc=…`，但雨滴效果模块仍通过没有查询参数的 URL 导入同一入口。浏览器把两者当成不同模块，首次上传预加载雨滴模块时再次执行主程序、重新挂载 React，清掉第一张图片；后台模型仍在运行。第二次上传时模块已缓存，因此通常正常。修复方式：带内容哈希的模块入口保持与依赖图相同的 URL；经典脚本继续使用版本参数，域名保护保留。

同时发现线上 HTML 指向 `index-BKwG5Ms8.js`，仍是首次发布版本：上传后才下载 176 MB FP32 模型，没有后台预加载、FP16、分块恢复与分阶段进度。10 月 4 日曾发布过优化构建，但没有提交到主站仓库。10 月 7 日镜像同步把这些未提交产物收进 stash，后续整站发布恢复了仓库内的旧版。现有源码中的优化没有丢失。

本次重新构建并提交优化产物，保留同源模型、GPU FP16、无 GPU 时的 FP32/WASM 回退、4 MB 静态分块、缓存、重试及真实进度。新增每个大文件同时下载 3 个分块，减少顺序请求的网络等待；按原始字节顺序组装，失败时等正在下载的分块结束并缓存，重试复用已完成部分。SHA-256 校验保持不变。

防止回退：`npm run test:effecter-release` 从 HTML 的实际入口追踪到分割 Worker，检查首次加载能力，而非只检查目录里是否残留新版文件。已接入站点完整性检查、CI、整站部署。部署包额外校验两种模型和运行时分块的长度及 SHA-256，避免 Git 忽略的大文件漏发。

部署包还会测试 HTML 的模块入口与雨滴模块的导入 URL 是否完全相同。旧保护构建已验证失败，修复后构建再验证通过。

发布必须提交 `projects/effecter/` 的小体积构建产物再部署；模型大文件及分块继续排除在 Git 外。保留其他项目的未提交修改，使用已提交版本的独立发布副本构建整站。

首次访问仍需下载模型及初始化，耗时取决于网络和设备。GPU 支持 FP16 时模型约 88 MB；不支持时使用约 176 MB 的 FP32 模型。不能承诺所有设备瞬间生成。
